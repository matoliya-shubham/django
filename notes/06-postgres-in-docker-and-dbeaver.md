# Chapter 6 — Postgres in Docker, DBeaver, `migrate`

**Rule: develop on the engine I deploy on.** sqlite uses *type affinity* — the
declared type is a hint, not a rule. It happily stored a 20-char value in a
`varchar(5)`; Postgres rejects it. So `max_length=200` was never enforced
locally, only by Django's own validation.

Switching **before** the first `migrate` means no data to port.

## docker-compose.yml — the 4 lines that matter

- **`image: postgres:17`** — pin the major. `:latest` will one day jump a major
  version and the container can't read its own volume.
- **`environment:`** — the image reads these **only on first boot with an empty
  volume**. Changing the password later does nothing.
- **`ports: "5433:5432"`** — `HOST:CONTAINER`. Without this the container runs
  but nothing outside Docker can reach it.
- **`volumes: pgdata:/var/lib/postgresql/data`** — the important one. Containers
  are disposable; without it `docker compose down` destroys every row.

`healthcheck` + `pg_isready` because Postgres reports "started" a few seconds
before it accepts connections. No `version:` key — that's Compose v1, obsolete.

## .env — one file, two consumers

| | Reads `.env`? |
|---|---|
| Docker Compose | **automatically** |
| Django/Python | **no** — needs `load_dotenv()` |

**JS:** same as Node, `dotenv.config()` is explicit there too.

`POSTGRES_HOST=localhost` is for Django only; Compose ignores it. If I ever
containerise Django, it becomes **`db`** — the service name — because containers
resolve each other by service name.

In settings I used `os.environ["X"]`, not `os.getenv("X")`: bracket access
raises `KeyError` at import naming the missing key. Fail loudly, fail early.

Driver is **`psycopg` v3**, not the `psycopg2-binary` most tutorials still show.
`ENGINE` is `django.db.backends.postgresql` either way.

## The bug: two Postgres servers, one port

`FATAL: role "django" does not exist` — but `psql -U django` worked *inside* the
container. So Django was hitting a different server.

```bash
lsof -nP -iTCP:5432 -sTCP:LISTEN
```

A Homebrew `postgresql@15` launch agent owned 5432. Docker reported no conflict
because Homebrew binds **specific** addresses (`127.0.0.1`, `::1`) and Docker
binds the **wildcard** (`*`) — macOS allows both, and **specific wins**.

Fix: moved my container to host port **5433**. Only the host side moved; inside,
Postgres still uses 5432. The container was recreated and **the data survived** —
the named volume proving its point.

**Remember:** when credentials "don't work" against a container, check what's
actually listening *before* touching the credentials.

## DBeaver

New Connection → PostgreSQL → host `localhost`, port **5433**, db
`django_tasks`, user `django`. Accept the driver download — that's **JDBC**,
a separate driver from psycopg (DBeaver is a Java app).

Host is `localhost`, not `db` — DBeaver runs on my Mac, same as Django.

**GOTCHA — no tables showing?** Check which *database* the editor is in, not
just the server: every cluster ships with an empty `postgres` maintenance
database and DBeaver can park there. `select current_database();` tells me.
Switch it with the toolbar dropdown.

## migrate

Same migration file, new backend:

| | sqlite | Postgres |
|---|---|---|
| `id` | `integer AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` |
| timestamps | `datetime` | `timestamp with time zone` |

Zero lines of `models.py` changed. That's what "migrations are Python objects,
not SQL" buys.

**19 migrations ran, not 1.** The rest belong to the built-in apps in
`INSTALLED_APPS` — that free admin panel and user system need tables. The order
interleaves apps because it's a dependency DAG being topologically sorted.

Two things to notice in the resulting schema:

- **`status` has no DB `DEFAULT`** despite `default="todo"`. Django applies
  defaults in Python on `save()`. Same for `choices` — no `CHECK` constraint.
  An INSERT typed into DBeaver bypasses both.
- **`django_migrations`** is the ledger, and it lives *in the database*. That's
  why a fresh DB replays all 19.

## Daily workflow

```bash
docker compose up -d      # start DB, first thing each day
docker compose ps         # up? healthy? which port?
docker compose logs -f db
docker compose down       # remove container, KEEP data
docker compose down -v    # ...and DESTROY data
docker compose exec db psql -U django -d django_tasks    # \dt  \d table  \q
```

`down` is safe thanks to the named volume. **`-v` is the dangerous one.**
